# Restyle a photo with AI — design (24 Oct 2026)

## Intent

The owner sends a plain phone photo of a product and says "restyle this photo", "make it aesthetic", „разкраси снимката", „направи я красива" — in any language, any wording that means *make this photo look good*. Claudia returns the **same product in an aesthetic, Instagram-ready photograph** (natural scene, soft light, shallow depth of field), made by Gemini's image model from the owner's photo as the reference. The owner can then post it, put it on the website as the item's photo, or both — with the usual ✅.

This is the picture the demo video and the Crossroads deck show ("Same cup. A picture worth posting."). Today the bot makes a cut-out on a branded card (`make_visual`); nothing in production restyles a photo. The owner's decision (24 Oct): **AI restyling only when asked**; the default photo flow does not change.

## Goals

- "Restyle this photo" / "make it aesthetic" (any language) → one restyled photograph of the same item in the chat within ~15 s, then the question *post it, website, or both*.
- The product must look like what is sold: same shape, colours, toppings, cup/plate, portion. Only the scene and light change.
- One free redo with a word: *darker*, *brighter*, *more minimal* (and their Bulgarian equivalents). The redo starts from the owner's original photo, not from the first result.
- The restyled photo can become the website photo of a menu item (the existing `set_item_image` path), with the owner's ✅ as for every site change.
- A monthly cap so a happy owner cannot run up a bill.
- Clean failure: when Gemini returns no image (safety refusal, people in the photo, outage), one short line to the owner and the card version (`make_visual`) instead.

## Non-goals (this build)

- No automatic restyling: the default "make a post from this photo" flow keeps producing the branded card.
- No named styles ("flat lay", "dark moody"); one house look plus the three redo words.
- No video.
- No AI label in captions **for now** (owner's decision, for the demo). The switch is built (see Labelling) and is off by default.
- No new UI: everything happens in the chat, with the existing ✅ / ✏️ / ❌ buttons.

## Anti-goals

- A restyle that changes the product (extra toppings, a different cup, invented text or logos). Worse than no restyle.
- Silent fallback: the owner must never be told "here is the restyled photo" and get the card.
- Spending on Gemini without the owner having asked.

## Where it fits

- **Trigger:** a new agent tool `restyle_photo`, registered only when `GEMINI_API_KEY` is set (like `make_visual` is registered only when the picture service is configured). A new system-prompt rule names the intents: restyle, make it aesthetic/beautiful/nicer, "make it look like a pro photo", „разкраси", „направи я красива / естетична / професионална", and the redo words. The rule says: only on request; the default photo flow stays `make_visual`.
- **Service:** `restylePhoto` in `src/visual/restyle.ts`, orchestrated like `makeVisual` (store + read + a `generate` function injected, so tests run without Gemini). Exposed through the existing `/api/visual` route as `kind: "restyle"` and the `VisualClient` (`restyle` method), so prompts, fallback and media saving live in one place. The route's 60 s budget holds: Gemini 1K edits take 8–20 s.
- **Model:** `gemini-nano-banana-2.1` (Gemini API, `POST /v1beta/interactions`, API key in `x-goog-api-key`), reference image + text prompt, `response_format: { type: "image", mime_type: "image/jpeg", aspect_ratio: "4:5", image_size: "1K" }`. 4:5 serves the Instagram post directly and crops well for the website card; the story 9:16 is made from the restyled photo by the existing story template. The output carries Google's SynthID watermark (invisible); keep it.
- **Prompt:** the template from `docs/research/2026-10-18-ai-visuals.md` §4 ("Use the uploaded photo as the exact reference… LOCK shape, proportions, colours, toppings, cup/plate, portion, label… CHANGE only the scene… LIGHT soft window light… AVOID extra food, hands, people, text, logos"), with the item name when known and one of three moods: default (light oak table by a window), *darker* (dark slate counter, low warm light), *brighter* (white marble, bright daylight), *minimal* (seamless warm greige backdrop, nothing else). The prompt is a constant in `restyle.ts`, not generated by the agent.
- **Result:** saved as venue media under `restyle/<source media id>/<n>.jpg` (JPEG, 1K, 4:5), sent to the chat by the tool with the caption "Restyled" / „Разкрасена", and recorded in `sentPhotos` as `make_visual` does, so a following `social_post` proposal does not send it twice. The tool returns `{ media_id, next }`, where `next` tells the agent to ask, in one short message, *post it / put it on the website as the photo of <item> / both*, and to list the redo words once.
- **Post:** `social_post` with the restyled media id, exactly as after `make_visual` (post 4:5; the story picture is rendered from it as today).
- **Website:** `propose_changes` with `set_item_image` on the item (the path `make_menu_photo` already uses). When the item is not clear from the photo or the words, the agent asks which item (one question, listing likely matches from `get_menu`).
- **Redo:** the owner answers with a mood word → `restyle_photo` again with the same source `media_id` and `mood`; the service keeps per-source generations.

## Limits and plans

- **Who:** the owner only (as `make_visual`).
- **Plan:** Social and Both plans (and grandfathered venues); on the Admin plan the tool answers with the upgrade line used for other social features. **Trial:** allowed, 5 source photos over the trial.
- **Cap:** 30 source photos per calendar month (venue time zone, as `monthWindow`); each source photo may have up to 3 generations (the first + two redos) — the second redo is the "one free redo" plus one spare, so the cap counts photos, not generations. The 31st photo gets one polite line ("That's the 30 restyles for this month; from the 1st again") and no call to Gemini. Counting = media saved under `restyle/` for the venue in the window (a store query by path prefix and date range; no new table).
- **Config:** `GEMINI_API_KEY` (present in production already), `RESTYLE_MONTHLY_LIMIT` (default 30), `RESTYLE_TRIAL_LIMIT` (default 5), `RESTYLE_MODEL` (default `gemini-nano-banana-2.1`).
- **Cost:** ≈ 0.03 € per generation at 1K; the cap bounds a venue at ≈ 3 €/month.

## Failure and fallback

- Gemini returns no image (safety block, "people" refusal, empty candidate), HTTP error, or timeout (service budget 40 s for the call): the tool returns `{ fallback: "card", reason }`; the agent tells the owner in one line in their language ("I couldn't restyle this one — here's the card version instead" / "…photos with people in them I can't restyle") and calls `make_visual` on the same photo. Never claim the card is the restyled photo.
- Product fidelity is not verified by a second model in this build (the research notes even the best models keep every detail ~28 % of the time on hard products). The owner sees the picture before ✅; the redo exists for that. A vision check is a later addition.
- Errors are logged by class only, never with the photo or the prompt output.

## Labelling (built, off)

- Venue setting `ai_label` (boolean, default false; `venue:set --ai-label on|off` in the console, no owner-facing switch yet). When on: captions made for a restyled picture end with "· made with AI" / „· създадено с AI", and `social_post` passes `is_ai_generated: true` to Instagram for that media. When off (now, for the demo): nothing is added. Note for later: Meta's `is_ai_generated` flag exists and the EU AI Act Art. 50 applies to generated scenes from Aug 2026 (grace to Dec 2026 for existing systems) — turn the switch on before scale, after legal advice.

## Tests

- `restyle.ts`: builds the right prompt for each mood and item name; saves media under the right path; counts photos not generations; returns `fallback` on an empty response, on HTTP 4xx/5xx and on timeout; never saves on fallback.
- Tool: owner-only; plan gate; trial and monthly caps with the venue's time zone; `sentPhotos` recorded; `next` text for the three outcomes; redo with a mood word reuses the source id.
- Prompt rule: a short list of trigger phrases (EN/BG) and the "only on request" sentence; the default photo flow unchanged (existing `make_visual` tests still pass).
- Route: `kind: "restyle"` wired with the secret; the client's `restyle` method; a smoke test against the real API behind an env flag (not in CI).

## Decisions from the builder check (24 Oct)

1. **Gemini contract.** Model `gemini-nano-banana-2.1` on the Gemini API: `POST https://generativelanguage.googleapis.com/v1beta/interactions`, header `x-goog-api-key: <GEMINI_API_KEY>`, body `{ model, input: [ { type: "text", text: <prompt> }, { type: "image", mime_type: "image/jpeg", data: <base64> } ], response_format: { type: "image", mime_type: "image/jpeg", aspect_ratio: "4:5", image_size: "1K" } }`; the picture comes back as `interaction.output_image.data` (base64). Sizes use an uppercase K. `@google/genai` is not a dependency: use `fetch`, and check the exact field names against https://ai.google.dev/gemini-api/docs/image-generation on the first run (one smoke test behind `RESTYLE_SMOKE=1`); if the field names differ, follow the docs, not this paragraph. The research note is now in this repo at `docs/research/2026-10-18-ai-visuals.md`; the full prompt (§4 "Image prompt template") with the four moods is the constant in `restyle.ts`:
   - default: "a light oak table by a window", "soft window light from the upper left, 5500K, gentle contact shadow"
   - darker: "a dark slate counter", "low warm side light, deep soft shadows"
   - brighter: "white marble", "bright even daylight, airy"
   - minimal: "a warm greige seamless backdrop in #d2c8b7, nothing else", "soft studio light"
   LOCK, CAMERA (slightly elevated 35 mm look, shallow depth of field, vertical 4:5, empty space at the top), REALISM and AVOID lines are the same for all four; `<item>` is the item name when known, else "the product in the photo".
2. **Fallback by intent.** If Gemini returns no image: for a post, the agent offers the card (`make_visual`) in the same message; for the website, `make_menu_photo` (never a card on the site — rule 16 stands); when the owner only said "restyle", the agent says it couldn't and asks whether to make the card or the website photo. The tool's `fallback` field carries `reason` ("refused" | "no_image" | "timeout" | "error"); the wording is the agent's, from the prompt rule.
3. **Where the key lives.** Production is one Vercel project, so `GEMINI_API_KEY` is on every function. Still, the tool is registered on a client capability — `d.visual.restyle` exists — not on the agent's env; the route registers `kind: "restyle"` only when the key is set. The same pattern as `make_menu_photo`.
4. **Cap accounting.** Count saved results (media under `restyle/`), not attempts: a refused or failed call costs the owner nothing. Two requests racing past the check is acceptable at this scale.
5. **Label mechanics.** Code, not the agent: `social_post` appends "· made with AI" / „· създадено с AI" to the caption and passes `is_ai_generated: true` to the Instagram publish call when the venue's `ai_label` is true **and** the media's path starts with `restyle/`. `ai_label` is a new nullable boolean column on venues (migration `2026-10-24-ai-label.sql`, null = off), on the Venue type and the store; `venue:set --ai-label on|off` is added to the console script. The Instagram publish code does not send `is_ai_generated` today: add the field (Graph API `POST /{ig_user_id}/media`, changelog 22 Jun 2026). Nothing is appended when the flag is off.
6. **Generations per photo.** The 4th request for the same source photo is refused with one line ("three versions is the most for one photo; send it again as a new photo if you want more") and no call. A `restyle/` media id is rejected as a source with the error "always start from the owner's photo", so redos start from the original.
7. **Trial and month.** Both caps apply; the stricter wins. The trial window is the venue's trial (`trial_started_at` + `TRIAL_DAYS`, as the trial change limit uses). Grandfathered venues (no plan, no trial) get the monthly 30.
