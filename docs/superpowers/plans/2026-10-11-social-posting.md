# Social posting (Facebook Page + Instagram, posts and stories) — design and plan

Status: requested by the owner 2026-10-11 ("start building") for the demo. Spec review was skipped at the owner's request; this file is the design and the plan. Branch `build/social` from main `a33beee`.

## Goal

The owner sends the bot a photo with a caption such as "Днешното предложение, пусни го във Facebook и Instagram". The agent proposes a social post (preview in the owner's language with the exact caption and the targets), the owner taps ✅, and the photo is published to the venue's own Facebook Page and/or Instagram professional account as a feed post and/or a story. The confirmation lists each network (published / will retry / error) with links. Undo deletes the Facebook post/story; Instagram media cannot be deleted through the API, so undo tells the owner to delete it by hand (with the link). The owner connects the Page and the Instagram account once from the dashboard; the last page of site creation (wizard done page) points them there. Prerequisites are written out for the owner in BG/EN wherever the connect buttons are.

Out of scope now: video/reels, carousels, scheduling UI beyond what `schedule_changes` already gives, App Review, posting by staff, automatic suggestion to post.

## Decisions

1. **Two destinations, two logins.** `facebook` (Facebook Login → Page access token, scopes `pages_manage_posts,pages_read_engagement,pages_show_list`) and `instagram` (Instagram API with Instagram Login, scopes `instagram_business_basic,instagram_business_content_publish`, same Meta app as the existing Instagram import: `INSTAGRAM_APP_ID` / `INSTAGRAM_APP_SECRET`, `IG_*` constants in `src/server/instagram.ts`). Instagram does not need a linked Page. Each destination has its own sync row, so a failure on one network never re-posts the other.
2. **Change entity.** New op/entity `social_post` (append to `Entity`, a new `SocialOpName = "social_post"` widening `Change.op` like `WpOpName`). `applyChange` and `SupabaseStore.writeEntity` treat it as a no-op exactly like `wp_*` (generalize the existing `isWpEntity` early returns with a new `isExternalEntity(e)` = wp_* or social_post; keep `isWpEntity` as is for the WordPress adapter). Row: `entity_id` = our media id; `after = { media_id, image_url, caption, targets: SocialTarget[] }` with `SocialTarget = "facebook_post" | "facebook_story" | "instagram_post" | "instagram_story"`, `before = null`. Undo = inverted row (`after = null`, `before` = the published row) → adapters delete what they can.
3. **Adapters** (`src/destinations/facebook.ts`, `src/destinations/instagram.ts`), registered in `ADAPTERS`, reusing the sync queue/store hook/tick retries unchanged. `relevant()` = `social_post` rows that contain a target for that network. Results stored in the sync row `result` (`{ published: [{ target, id, permalink }] }`), and the publish for a target is skipped on retry if the previous attempt's stored result already has it (read the latest done/pending row result for the same change set + destination before publishing; keep partial results on failure by writing them into `result` even when the attempt fails — extend `runSync` minimally: a PushResult may carry `partial` that is persisted on failure).
   - Facebook (Graph `v25.0`, Page token): post = `POST /{page-id}/photos` `{ url, caption, published: true }` → `{ id, post_id }`; permalink via `GET /{post_id}?fields=permalink_url`. Story = `POST /{page-id}/photos` `{ url, published: false }` → photo id, then `POST /{page-id}/photo_stories` `{ photo_id }` → `{ post_id }`. Undo = `DELETE /{post_id}` for each published id (treat 404 as already deleted).
   - Instagram (graph.instagram.com `v25.0`, long-lived user token, ig user id from `/me?fields=user_id,username`): post = `POST /{ig-user-id}/media` `{ image_url, caption }` → container id, poll `GET /{container}?fields=status_code` until `FINISHED` (max ~10 tries × 2 s; `ERROR`/`EXPIRED` → non-retryable error), then `POST /{ig-user-id}/media_publish` `{ creation_id }` → media id; permalink via `GET /{media-id}?fields=permalink`. Story = same with `media_type: "STORIES"` and no caption. Undo = no API call; the push returns ok with a manual-delete note and the permalinks. Images must be JPEG for Instagram: if the media's content type is not JPEG, refuse at proposal time with a clear tool error (Telegram photos are JPEG). Token refresh: if the stored token is older than 30 days, call `GET https://graph.instagram.com/refresh_access_token?grant_type=ig_refresh_token&access_token=…` before publishing and store the new token (encrypted).
   - Owner-facing lines via `syncLines`: map kind → "Facebook"/"Instagram" (keep WordPress); on done append links when the result has permalinks; for the Instagram undo note the line is BG "Instagram: изтрийте публикацията ръчно: <link>" / EN "Instagram: delete the post by hand: <link>". Error codes mapped to BG/EN in `wp-errors.ts` style (a token that no longer works → "свържете отново от таблото" / "reconnect from the dashboard").
4. **Connection flows** (admin-key authenticated, signed state like the Instagram import, secrets encrypted with `DESTINATION_SECRET_KEY` via `upsertDestination`):
   - `GET /api/admin/[slug]/social/facebook/start?key=` → `https://www.facebook.com/v25.0/dialog/oauth?client_id=META_APP_ID&redirect_uri=<base>/api/social/facebook/callback&scope=…&state=…`. Callback: code → user token (`/oauth/access_token`) → long-lived user token (`grant_type=fb_exchange_token`) → `GET /me/accounts?fields=id,name,access_token,tasks`. One page → store it; several → render a small BG/EN chooser page whose links carry a signed, short-lived state containing the encrypted long-lived user token; selecting re-reads `/me/accounts` and stores the chosen page. Store config `{ page_id, page_name, connected_at }`, secrets `{ page_token }`.
   - `GET /api/admin/[slug]/social/instagram/start?key=` → `IG_AUTHORIZE_URL` with the two publishing scopes and redirect `<base>/api/social/instagram/callback`. Callback: code → short-lived token (`IG_TOKEN_URL`) → long-lived (`GET https://graph.instagram.com/access_token?grant_type=ig_exchange_token&client_secret=…&access_token=…`) → `/me?fields=user_id,username,account_type`. Refuse personal accounts with the prerequisite message. Store config `{ ig_user_id, username, connected_at, token_refreshed_at }`, secrets `{ token }`.
   - Disconnect: `POST /api/admin/[slug]/social` `{ action: "disconnect", kind }`.
   - New env: `META_APP_ID` (public app id, config only). Without `META_APP_ID`/`META_APP_SECRET` the Facebook button is hidden; without `INSTAGRAM_APP_ID`/`INSTAGRAM_APP_SECRET` the Instagram button is hidden. Redirect URIs the owner must add in the Meta app: `<base>/api/social/facebook/callback` (Facebook Login → Valid OAuth Redirect URIs) and `<base>/api/social/instagram/callback` (Instagram → Business login settings).
5. **Agent tool** `social_post` (owner only; registered only when a `facebook` or `instagram` destination is connected): input `{ summary_bg, summary_en, media_id, caption, targets }`; validates the media belongs to the venue, caption ≤ 2,200 chars and ≤ 30 hashtags when an Instagram post is targeted, targets only for connected networks; proposes a change set with one `social_post` row through the same propose/ensureNoPending path as `wp-tools.ts`. Preview lines (new `src/domain/social-preview.ts`, wired into `renderPreview`): BG "• Публикация: Facebook (пост, история), Instagram (пост)" + the caption quoted on the next lines; inverted row: "• Премахва публикацията: …". Prompt rule appended: when the owner asks to post/publish a photo on Facebook/Instagram, use `social_post` with the photo's media_id, write the caption in the venue's default language (Bulgarian for BG venues) unless the owner gives the text, default targets = feed post on every connected network, add stories only when asked ("история"/"story").
6. **Dashboard card** `SocialCard` (rendered in `AdminPanel` next to the WordPress card, one import + one line): status per network, Connect/Disconnect buttons, the last five posts from the sync rows with links, and the prerequisites in BG/EN:
   - Instagram: a professional account (Business or Creator) — Settings → Account type and tools → Switch to professional account; while the app is in development, the account must be added as Instagram Tester and accept the invite.
   - Facebook: a Facebook Page for the venue where you are an admin (or have full control); you sign in with your personal Facebook profile that manages the Page.
   - Posts are public on your profile/Page; undo deletes Facebook posts, Instagram posts must be deleted by hand.
7. **Wizard done page** (`app/new/[id]/done/DoneStatus.tsx`, last page of site creation): a short "Свържете Facebook и Instagram" / "Connect Facebook and Instagram" block with one sentence of prerequisites and a link to `/admin/<slug>?key=<adminKey>#social`. Minimal edit (the templates session owns this file; tell it).
8. **DB**: `supabase/schema-integrations.sql` — extend `venue_destinations_kind_check` to include `'facebook','instagram'` (drop/add constraint, idempotent) and `changes_entity_check` to include `'social_post'`. Apply live ONLY this file: `npm run db:apply -- schema-integrations.sql` (never the bare db:apply: main's schema.sql would narrow the templates constraint). `check:rls` after.
9. **i18n**: every owner-facing string BG first, natural; dictionary keys appended at the end of `en` and `bg`.

Adapters + sync extensions (partial results, per-target idempotency, lines with links, manual-delete note) + tests (`test/destinations-social.test.ts`): publish all four targets, retry after a failure does not duplicate a published target, undo deletes FB and returns the IG note, token-invalid → error line "reconnect".
